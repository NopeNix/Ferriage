# Session 009 — Phase 1.5: deploy + health gate

**Phase 1.5 is done.** `POST /stacks/{name}/deploy` brings a stack
dir's Compose file up via the `docker compose` CLI and gates on the
daemon-reported container health until every health-checked
container is `healthy` (no-healthcheck containers count once
running). Stacks are left running on gate failure — Ferriage never
tears down a failed deploy on its own.

**Decision (no ADR; one-line, reversible):** deploy shells out to
`docker compose`, not compose-go. The CLI is already on operator
hosts; compose-go would add a dependency for this milestone. Phase 3
can revisit. Gate: pure Engine API (`ContainerList` + inspect).
Timeout 120s / poll 2s, both via `Config`.

Implemented (Layer 1 green, `scripts/test.sh --fast`: 4/0):

- `internal/deploy` — `Deploy` (`up -d` then health gate),
  `Result`/`Svc` JSON, `POST /stacks/{name}/deploy` handler
  (404 when the stack dir/compose file is missing; 502 with the
  per-service state when the gate times out)
- `cmd/peer` — one `deploy.Register` line

**Live proof** (home box, real daemon):

- healthy stack → `{"healthy":true}` in ~6s; daemon confirms
  `(healthy)`; volume data intact after redeploy (idempotent)
- no-healthcheck stack → `healthy:true` immediately
- would-never-be-healthy stack → gate times out at 120s, **502**
  with `app(unhealthy)`; stack left running (compose `--wait`
  was dropped for this reason — it fails the same way but hides
  the per-service state behind its own exit code)
- adopted view (`GET /stacks`) shows all three stacks running

Probes cleaned up (containers, volumes, `/tmp` state dirs).
